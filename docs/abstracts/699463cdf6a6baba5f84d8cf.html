Introduction

Neuroimaging datasets are now large, multimodal, and increasingly shared, but results remain highly sensitive to analytical choices that are often incompletely reported and difficult to reproduce. Navigating the 'garden of forking paths' in analysis choices leads to substantial heterogeneity in methodological decisions. Standards such as the Brain Imaging Data Structure (BIDS) and robust pipelines (e.g., fMRIPrep) have improved dataset portability and preprocessing quality, but they do not solve the end-to-end problem of translating an analysis intent into a transparent, executable workflow.

Large language models (LLMs) can draft analysis code from natural-language prompts, yet free-form code generation is not verifiable: models may call invalid parameters, violate basic order-of-operations, or apply inappropriate inference procedures, where failure modes undermine scientific validity.

We present Brain Researcher, a neuroimaging system that converts natural-language analysis requests into verifiable, schema-constrained tool invocations over a curated library of >2,000 functions wrapping established packages (NiWrap3, FSL, SPM, Nilearn). Rather than emitting scripts, Brain Researcher plans within a typed neuroanalytic action space, executes steps in version-pinned containers, and produces auditable logs and intermediate artifacts (Figure 1a).

Methods

System architecture and user interface. Brain Researcher translates a natural-language request into an executable, auditable workflow without emitting free-form analysis scripts as the primary interface. Users provide prompts through (i) a Web UI oriented toward end-to-end reasoning and inspection (Figure 2a), or (ii) a CLI oriented toward rapid iteration and tool use (Figure 2b). The system returns a structured plan (tool IDs + parameters), citations for choice-dependent decisions, and a run record containing logs and artifacts (e.g., generated commands, intermediate files, reports, and statistical maps) (Figure 1c).

Planner and schema validation. An LLM-based planner proposes a workflow as a typed sequence of tool calls that must validate against a formal schema before execution, under the ReAct2 framework, implemented using LangGraph1.  In the evaluation reported here, the default planner model was Gemini 2.0 Flash; the planner is modular and can be swapped. The tool library contains >2,000 wrapped operations spanning data handling, preprocessing, GLM modeling, reporting, and ML-style analyses, interfacing with established software stacks (NiWrap, FSL, SPM, Nilearn, PyTorch) (Figure 2c). Each tool specification encodes required inputs/outputs, allowed parameter types/ranges, and logical constraints (e.g., motion correction precedes spatial smoothing; group models require compatible spaces). Invalid tool calls (non-existent parameters, incompatible file types, or violated preconditions) are rejected and returned to the planner as explicit errors for replanning.

Knowledge graph grounding and evidence capture. To reduce methodologically plausible but contextually inappropriate choices, planning is coupled to a retrieval layer implemented as a Neo4j property-graph knowledge base that indexes (i) BIDS dataset structure/metadata, (ii) available derivatives when present, and (iii) tool schemas with preconditions and version metadata. For choice-dependent decisions (e.g., nuisance models, filtering cutoffs, multiple-comparisons procedures), the planner retrieves relevant context from package documentation (e.g., the SPM12 manual, FSL/FEAT documentation, and Nilearn documentation) and a small set of canonical fMRI methods references for nuisance modeling and multiple-comparisons control, and attaches citations to the decision. Provenance (source pointer, tool/software version, and the final resolved parameters) is stored alongside the executed plan.

Data access, execution, and failure handling. Brain Researcher is BIDS-native: it scans an input directory and builds a dataset index (subjects, sessions, modalities, tasks, events/confounds) that parameterizes downstream steps. Execution occurs in version-pinned containers (through Neurodesk4) to isolate the host environment and support reproducibility. The executor records structured logs, intermediate artifacts, and failure signals; when a step fails (e.g., missing metadata or resource limits), the planner can replan by adjusting parameters or selecting alternative implementations, with optional human-in-the-loop intervention.

Evaluation. We assessed (i) generalizability across a benchmark of natural-language analysis requests on public datasets (OpenNeuro and nilearn examples) (Figure 2F), and (ii) replicability via blinded reconstruction of a published fMRI analysis using only the Methods/Results text. We compared against a general-purpose coding assistant (Claude Code). Outcomes included workflow executability, rate of invalid parameterization/order violations, iterations/time-to-solution, and (when reference results were available) agreement between reproduced and reference figures (Figure 2).

Results

Coverage and executability. Across 80 natural-language requests spanning data ingestion, preprocessing, statistical modeling, and ML-style analyses, Brain Researcher produced an executable, schema-validated tool plan in 56/80 (70%) cases (Figure 2d, left). For successful runs, the system returned (i) a validated plan (tool IDs + resolved parameters), (ii) a version-pinned/containerized execution trace, and (iii) rerunnable artifacts (logs, intermediate outputs, reports, and statistical maps). Most failures reflected incomplete/non-standard dataset metadata that prevented automatic parameterization of downstream steps.

Benchmark versus unconstrained code generation. We evaluated whether constraining workflow generation improves reliability compared with the common baseline of free-form LLM coding. In the baseline condition, Claude Code attempted to solve each benchmark entry by generating analysis code/commands directly. In the constrained condition, we exposed Brain Researcher as an MCP tool layer that Claude Code could call: the agent still performs task interpretation and orchestration, but core analysis steps must be expressed as schema-validated tool calls drawn from Brain Researcher’s >2,000-operation library (with typed inputs/outputs, parameter bounds, and preconditions). The rationale is that most “LLM for science” failures arise not from missing syntax knowledge, but from unverifiable method choices (invalid arguments, incompatible inputs, and incorrect sequencing) that are hard to detect without an explicit action space.

On our benchmark entries, Claude Code + Brain Researcher MCP achieved 53 successful entries with 1.19 attempts/entry, compared with Claude Code at 51 successful entries and 1.83 attempts/entry (≈35% fewer attempts, see Figure 2d right). Here, an “attempt” corresponds to an end-to-end propose→validate→execute cycle, including any retries triggered by invalid tool calls or failed executions. In addition to improved completion and fewer retries, the constrained setup produced auditable run records: for choice-dependent decisions (e.g., nuisance modeling, filtering cutoffs, multiple-comparisons procedures), the system attached citations to package documentation (SPM12; FSL/FEAT; Nilearn) and canonical methods references when applicable, and recorded tool/software versions and final resolved parameters. Representative baseline vs Brain Researcher–grounded inputs/outputs (figures and artifacts) are shown in Figure 2.

Replication from text. To test whether Brain Researcher can bridge narrative methods descriptions to executable pipelines, we conducted a timed, blinded reconstruction of six figures in published fMRI study5 using only the paper’s Methods/Results text (Figure 2g). The target was not merely “code that runs,” but a reconstruction that (i) recovers the major analysis stages, (ii) matches reported settings where specified (e.g., thresholding choices), and (iii) yields a rerunnable workflow with explicit provenance (plan + tool/version records + artifacts). We compared three workflows: Brain Researcher–empowered Claude Code, Claude Code (unconstrained), and Claude-assisted manual coding.

The Brain Researcher–grounded setup reached a comparable reconstruction with fewer iterations and less time: 6.5 min/figure with 2 iterations/figure for Brain Researcher–empowered Claude Code, versus 8 min/figure with 4 iterations/figure for Claude Code, and 45 min/figure for Claude-assisted manual coding (≈1.2× faster than Claude Code and ≈6.9× faster than Claude-assisted coding, see Figure 2E). Importantly, when the paper underspecified details (a common reproducibility bottleneck), the Brain Researcher pipeline either surfaced missing requirements explicitly or selected a documented default and recorded that choice for audit, rather than silently filling gaps. Figure 2 summarizes benchmark outcomes and replication fidelity, and includes representative reconstructions and resulting artifacts.

Conclusion

Brain Researcher demonstrates a practical alternative to free-form LLM code generation for neuroimaging: treat the model as a planner over a verifiable action space, and couple planning to version-pinned execution with audit trails. By enforcing schema validation and explicit constraints, the system reduces hallucination-driven failures and shifts evaluation from “did the code run?” to “was the analysis methodologically appropriate?”

This approach is not a substitute for good reporting or standards. Performance degrades when datasets deviate from BIDS conventions or when published methods omit key details, reinforcing the value of standardized metadata and transparent reporting. Future work will expand tool coverage, improve robustness to non-standard datasets, and formalize evaluation across more published studies and modalities. More broadly, trustworthy AI for neuroscience will require hybrid architectures that combine language-based reasoning with explicit constraints, provenance, and reproducible execution environments.
