Introduction

With a varying range of both raw and derived multimodal data being made publicly available by the community, the field of neuroimaging has been transitioning to a new era of big data.1 This scale of data enables more robust, reproducible and impactful neuroscientific research.2 To facilitate this type of research, researchers require the necessary tools to interface with the vast amount of data available. The Brain Imaging Data Structure (BIDS) standard was developed to promote consistent organization of datasets across research groups, improving accessibility.3 Similarly, platforms, such as OpenNeuro, have further enhanced data sharing and use by making data available via cloud storage providers, like Amazon Web Services (AWS).1 PyBIDS is a set of tools developed for the purposes of working with BIDS datasets and commonly employed within processing and analytical workflows to facilitate dataset querying and manipulation. While stable, there were community-noted scalability concerns due to the performance of indexing large datasets. To address this, we originally developed a framework, bids2table, aimed at enabling flexible and efficient aggregation of large-scale neuroimaging data by leveraging development from the broader data science community. In this work, we present bids2table 2.0, a re-engineered, updated framework to our original tool. Updates to this framework include additional performance gains and newly added cloud integration to support the querying and manipulation of neuroimaging datasets stored on platforms such as OpenNeuro. To illustrate these new gains and features, we benchmark our tool on datasets stored locally and on OpenNeuro.

Methods

Taking advantage of the BIDS organization, our framework traverses neuroimaging datasets and converts them into PyArrow tables, storing standard BIDS entities into individual columns. Additional BIDS entities, often introduced as part of derived datasets, are stored as structured lists as part of a separate table column. Further, information such as the file name and file location are stored in the table to facilitate easy retrieval of both imaging data and its associated JSON sidecar metadata. To improve indexing performance, metadata is not initially loaded and stored as part of the table, but instead optionally loaded in a separate function call. Loading of metadata follows a top-down approach, loading each JSON sidecar found, in order to support the BIDS inheritance principle. Using bids2table 2.0, in-memory tables are first created for indexing the dataset and optionally stored to disk using the Apache Parquet file format, providing improved data compression. Moreover, the use of PyArrow tables enables straightforward conversion into common, more human-readable data science dataframe formats, such as Pandas or Polars. Efficient parallelization is achieved by leveraging the hierarchical structure of BIDS datasets, distributing subject-level directories across multiple workers for distributed execution. Pairing together with Python’s native path library, an external library, cloudpathlib, is integrated into bids2table 2.0 to support direct retrieval of datasets stored on cloud platforms using the same interface as locally stored datasets. Moreover, the updated framework supports simultaneous transformation of multiple bids datasets.

To demonstrate the improvements made in bids2table 2.0, we benchmarked and compared the updated framework with our original implementation and PyBIDS. We first compared both single and multi-threaded indexing performance (time to index) on a locally stored copy of the Nathan Kline Institute Rockland Sample (NKI-RS) dataset (n=1334 participants, 1.5TB).4 Additionally, we examined the sizes of the indexed tables when stored on disk. We then performed the same benchmarks for indexing and saving to disk, all of the datasets (n=66,000+ participants across 1,500+ datasets) publicly available on the OpenNeuro platform1 using our updated framework. Notably, only single-threaded performance applied to the local dataset was examined for PyBIDS due to a lack of multi-threading and cloud support. Following indexing benchmarks, we compared performance for querying the raw BIDS dataset Chinese Color Nest Project (CCNP; n=195 participants)5 using PyBIDS, bids2table, and bids2table 2.0. Queries included extraction of subjects, identification of functional neuroimaging data, and probing of metadata in order to identify scans of interest. 

All benchmarks were performed with an initial warmup run, followed by 10 iterations, with median benchmark metrics reported. Results

We previously demonstrated that the original implementation of bids2table outperformed PyBIDS. In our updated comparisons, the performance gains previously seen are confirmed in the updated benchmarks. In the re-engineered bids2table 2.0, we demonstrate measurable improvements over the previous version in both performance and file size. Performance benchmarks are presented in Figure 2a. Examining single-threaded performance, the original bids2table implementation demonstrated a 95x improvement to PyBIDS at 23.63s and 2233.34s for indexing respectively. With bids2table 2.0, indexing completed in 5.04s, exhibiting a performance gain of 440x over PyBIDS and over 4x from the original framework. In multi-threaded performance, bids2table 2.0 demonstrated a near 2x gain compared to its predecessor, requiring 2.27s to index the local dataset compared to 3.99s. The indexing of all publicly available OpenNeuro datasets was performed using multi-threaded indexing and took approximately 374s — a feat impossible with pyBIDS.

When saved to disk, the file sizes of the stored tables showed a similar trend (figure 2b). PyBIDS, which stores its table using a database, required 437.24 MB to store the NKI-RS dataset. The original implementation of bids2table required 3.92 and 3.68 MB for single- and multi-threaded indexing respectively of the same dataset, with the discrepancy arising from how the dataset itself is stored (single file vs multiple files). Nonetheless, this presented an over 110x decrease in space required compared to PyBIDS. Finally, bids2table 2.0 required only 0.45 MB, a near 970x decrease compared to PyBIDS and 8x improvement compared to its predecessor. For cloud-stored datasets, bids2table 2.0 required only 22 MB to store all of the datasets available.

For our final benchmarks, examined the performance of applying various queries to the raw CCNP BIDS dataset. Both the original and updated implementations of bids2table performed similarly compared to each other, while outperforming PyBIDS. When querying for all unique subjects of the dataset, PyBIDS took 572ms, while bids2table and bids2table 2.0 took 0.056ms and 0.046ms respectively, demonstrating a 10,000x improvement when using bids2table. Similarly, when querying for functional MRI data, PyBIDS took 16ms, bids2table took 0.5ms and bids2table 2.0 took 0.1ms. Queries related to metadata took 9ms using PyBIDS, and 0.3ms and 0.2ms using the original and updated implementations of bids2table. Finally, when querying for data from participants scanned at a particular time of day (morning), PyBIDS required 669ms, while bids2table and bids2table 2.0 were notably faster at 0.3 and 0.2ms apiece. Figure 2c demonstrates these querying benchmarks. All querying comparisons also confirm previously seen benchmarks during our original benchmarks.

Conclusion

In this work, we present bids2table 2.0, a re-engineered and updated framework of our original tool designed for efficiently indexing large-scale raw neuroimaging data and its derivatives. We demonstrate its utility by comparing the improved tool against both the original implementation and the widely used PyBIDS package. Benchmarks were conducted across several scenarios, including indexing local and cloud datasets, as well as evaluating performance under single-threaded and multi-threaded execution where applicable. Additionally, we examined the storage requirements for these indexed datasets on disk. Across all benchmarks, we observed quantifiable performance improvements, not only when comparing bids2table to PyBIDS, but also between bids2table 2.0 and its predecessor.

Although all these tools are designed for similar purposes and built within the Python ecosystem, it is important to note that each relies on a distinct set of dependencies with varying implementations, which can significantly influence performance. Our development of bids2table 2.0, alongside its original version, was motivated by a goal to streamline analyses using modern data science frameworks. Through this work, we also provide illustrative examples of how bids2table can be applied to large-scale neuroimaging data analysis, highlighting both its efficiency and practical utility.

The next steps of this project will include the unification of tools in the field, where we will partner with the rest of the PyBIDS team and several of its power users, to ensure complete and robust API coverage, such that the much lighter-weight and more maintainable bids2table 2.0 can be adopted and recommended as the next generation data crawler for the BIDS ecosystem.
