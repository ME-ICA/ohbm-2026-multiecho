Introduction

CBRAIN^1 (https://cbrain.ca) is an open source, web-based, collaborative research software platform that addresses major challenges in big data research. CBRAIN allows scientists to launch, monitor and share large-scale big data analyses using advanced scientific tools through an easy to use web-based interface.

Since 2015 CBRAIN leveraged Boutiques^2 to easily integrate new tools. Boutiques allows a tool to be deployed in CBRAIN using a simple JSON descriptor that specifies the command line, the list of parameters and input/output validation rules. Based upon this descriptor, CBRAIN automatically builds the user interface allowing researchers to set parameters and launch the tool.

Over the years, the need arose to add some CBRAIN specific behaviour (eg., advanced file handling, data management...) that fall outside the scope of the core Boutiques standard. Boutiques descriptor used within CBRAIN define a custom section to leverage specific libraries, enabling the seamless integration of diverse pipelines.

Methods

In CBRAIN, tools have been integrated via three different methods since the platforms inception in 2009:

2009 Ruby on Rails Code and Web Page Templates: 

In the original methods for tool integration in CBRAIN, a CBRAIN developer would code the user interface to the tool directly using Ruby code and templates. While highly customizable, it represented specific codings for each tool that were not reusable.


2015 Integration with Boutiques Declarative Framework:

Support was added to CBRAIN using Boutiques descriptors for automated tool integration. The code to run the tool and the user interface are generated in CBRAIN at boot time based on templates. Even though this method facilitated tool integration, some limitations persisted, including difficulties in developing, maintaining and documenting the logic related to custom Boutiques descriptor properties. Using Boutiques allowed for easier tool integration, giving a uniform user experience. However, the logic for Boutiques custom properties is scattered through the codebase, and maintenance and documentation are challenging.


2020 to Present: Runtime Integration with Boutiques Descriptors:

CBRAIN uses Boutiques descriptors but with a new integration method performed at runtime using hooks and a library of modules where each module handles one custom property/keyword. With this method, tool developers can easily introduce CBRAIN-specific properties to Boutiques that enhance the standard behavior. This method is easy to maintain and facilitates the creation of new modules to add functionality when needed.  It offers the ability to overwrite or modify ttask submission or execution logic, such that each specific customization is easy to separate, and documentation for each module can be generated by rdoc.

2025 Container-bindmount-plugins:

In addition, the creation within CBRAIN of Container-bindmount-plugins allows the tool or integration programmer to automatically mount a folder within the original container which can remain unmodified from the container created by the tool maintainer. This ability enables the addition of wrappers around the tool to handle specific needs without requiring changes to the original tool container or to create a specific pipeline for integration.

Results

Gaps between generic tool descriptors and platform specific requirements, can be filled by specific Ruby code.
These behaviors are modular and can be stacked so as to handle complex integration scenarios without modifying the core tool code.

These extensions can be categorized in three functional groups:

- Input pre-processing: preparing the execution environment (e.g BoutiquesInputSubDirMaker for creating directory hierarchies).

- Execution configuration: handling complex workflows, such as tools requiring a two-stage execution (e.g., configuration generation followed by analysis). To avoid creating `hybrid container` patched with internal wrappers, CBRAIN now implements a plugins-container-bindmount point. This utility allows for dynamic mounting of wrappers for example into the container at runtime, leaving the original container image untouched. 

- Output post-processing: identifying, verifying, and registering output files back into the platform’s database (eg: BoutiquesInputCacheCleaner to remove cached file inputs after successful task completion)

Conclusion

This architecture of CBRAIN Boutiques library is a facilitator in tool integration. By adding essential pre and post processing behaviors, it fills the gap between the standardized execution definition of Boutiques descriptor and the operational requirements within CBRAIN.


In addition the ability to add companion code, such as a wrapper script via some mounted container, it makes tool integration in CBRAIN highly versatile. This allows, for example, the pipeline to be run twice (for initialisation and run) or to perform various quality control actions once the main tool has completed.
